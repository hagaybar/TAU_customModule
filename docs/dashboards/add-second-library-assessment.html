CenLib Shelf-Map · Scoping Assessment

Adding a second TAU library to the Shelf-Map feature

How much work it takes to onboard a second physical library (its own building, its own CSV rows, its own floor plans) — across the Primo custom module (consumer), the Primo-Maps admin (producer), and the CloudFront data pipeline.

Repos: TAU_customModule + NDE_MAPS_MANGER Currently live for: 1 library (Sourasky Central) Assessment date: 2026-07-13 Basis: source read + 3 code sweeps
Not a data-entry task. It's a small engineering project on the producer side plus a large map/data-authoring effort — weeks-scale, not a config tweak.

The feature's data format carries a libraryName on every row, so the consumer add-on already looks up any number of libraries with no rearchitecting. But every system around that format is shaped for one building: the admin app, its Lambdas, and its validation are hardcoded to "Sourasky" and a fixed 3-floor set, and even the consumer's asset paths (/maps/floor_{n}.svg) have no library dimension — so a second building's floors collide with Sourasky's. "The architecture is multi-library" is true of the data shape only.

01

The core finding: a one-sided readiness

Consumer — the Primo add-on READY

  • Lookup is multi-library ("MDM"). Matches on (library + collection + Dewey range) → shelf.
  • Adding a library = 1 config entry in library.config.ts (+ exact DOM strings).
  • Bilingual index, overlapping ranges, multi-shelf dialog all already handled.
  • No rearchitecting needed to find a second library.

Producer + asset paths SINGLE-BUILDING

  • Admin app hardcodes SINGLE_LIBRARY = "Sourasky"; no library selector exists.
  • Floor set pinned to {0,1,2} in 6+ files (validation + staging + upload).
  • SVG paths are flat: maps/floor_{n}.svg — building 2 would overwrite building 1.
  • Validation keys shelves by floor only — two buildings on floor "1" get conflated.

Sourasky owns floor_0/1/2.svg and one shared mapping.csv. A second building needs its own floor plans — how you lay them out cascades through both repos.

Option B is a false economy. The expensive producer work (library scoping, the SINGLE_LIBRARY auto-fill, the floor whitelist, library-aware validation) has to happen either way. B only saves SVG-path namespacing — and buys a broken floor label in return. Recommend A unless the second library is tiny/temporary.
Two related sub-decisions:  (1) keep one shared CSV + add a library filter to the editor (recommended, lowest consumer blast radius) vs. one CSV per library;  (2) does the new building reuse floor numbering 0/1/2 or have different floors?
04

Work breakdown by area

A · Producer retrofit primo_maps / NDE_MAPS_MANGERLARGE

Vanilla-JS admin SPA on S3/CloudFront (Cognito auth, admin/editor roles) + ~25 Lambdas + a staging→promote publish flow. To genuinely handle a 2nd library:

  1. Library dimension in the admin UI — today the edit dialog auto-fills SINGLE_LIBRARY and renders no library field; new rows default to Sourasky. Needs a selector + per-library scoping so building 2 isn't edited blind (or mislabeled).
  2. Namespace SVG storage per library (Option A) across uploadSvg, uploadStagingSvg, listSvg, deleteSvg, versioning, and svg-loader.js.
  3. Make the floor set configurable — remove/parameterize the {0,1,2} / FLOOR_VALUES hardcodes in validateBundle.mjs, range-validation.mjs, fetch-floor-svgs.mjs, validateStaging.mjs, data-model.js, uploadStagingSvg.mjs.
  4. Make validation library-aware — the bundle check keys shelf-sets by floor alone; two buildings sharing floor numbers would conflate. Key by (library, floor).
  5. Add an "onboard a library" runbook — none exists in that repo today.
There is no supported end-to-end path today — a librarian cannot "add a library" through the UI as it stands. This is the dominant code effort.
B · Consumer changes TAU_customModuleSMALL
  1. Add one LibraryConfig to library.config.ts: exact Hebrew nameHe (must byte-match Primo's .getit-library-title), English name, svgPath, and every sub-location's exact nameHe. Requires field-capture of the live DOM strings.
  2. Under Option A, 3 small edits: the offline-fallback regex in map-asset-fallback.ts (only matches /maps/floor_(\d+).svg), the hardcoded FLOORS=[0,1,2] in scripts/sync-map-assets.mjs, and the bundled-asset layout under src/assets/cenlib-map/.
  3. Refresh the offline fallback (npm run sync:map-assets) and commit.
Ignore location-filter.config.ts — it looks relevant but is imported nowhere (dead code). Gating is LIBRARY_CONFIG + the CDN CSV only.

05

Risks & constraints to hold

🔗
Producer↔consumer parity contract (issue #100)
Any change to the producer's range/validation logic must stay behaviorally identical to the consumer's compareDeweyNumbers() / isInDeweyRange(). Don't weaken the parity fixtures/tests the producer's WORKFLOW.md protects.
🏢
Floor-set hardcode {0,1,2}
If the new building's floors aren't 0/1/2 (a basement -1, floors 0–4, …), more spots need widening on both sides.
🗃️
Shared CSV without UI scoping is unsafe to edit
Until the admin is made library-aware, a librarian editing building 2 sees building 1's rows intermixed, and saves re-stamp them "Sourasky". This is why a one-time hand-load is not maintainable.
🧪
Existing data isn't fully clean
40 of 386 svgCodes already mismatch their SVG IDs. Onboard the new library to a clean pass rather than inheriting that debt.
